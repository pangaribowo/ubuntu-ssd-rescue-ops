# Technical Triage: DNS Resolver Pollution in Chroot & Dual-Boot Environments

## 1. Problem Statement & Incident Context

After managing an external Ubuntu installation from a Windows host using a WSL2 `chroot` bridge, the system was booted natively via bare-metal dual-boot. Although the Wi-Fi interface successfully associated with the local access point, obtained an IPv4 lease via DHCP, and established default routing, all domain name resolution failed across user-space applications (browsers, `curl`, `apt`, `git`).

```
$ ping -c 1 8.8.8.8
1 packets transmitted, 1 received, 0% packet loss  <-- ICMP IP Routing OK

$ ping -c 1 google.com
ping: google.com: Temporary failure in name resolution  <-- DNS Lookup FAILED
```

---

## 2. Root Cause Analysis

### 2.1 The Canonical Ubuntu DNS Architecture (`systemd-resolved`)

In modern Ubuntu installations (18.04+ through 24.04 LTS), name resolution is managed by `systemd-resolved`:

1. **Daemon:** `systemd-resolved.service` listens locally on the loopback address `127.0.0.53:53` as a caching stub resolver.
2. **Dynamic Generation:** When NetworkManager connects to an AP, it communicates the DHCP-provided DNS servers to `systemd-resolved` via D-Bus (`org.freedesktop.resolve1`).
3. **Stub File:** `systemd-resolved` writes the active configuration to the transient runtime filesystem at `/run/systemd/resolve/stub-resolv.conf`:
   ```ini
   nameserver 127.0.0.53
   options edns0 trust-ad
   search localdomain
   ```
4. **Symlink:** On the root filesystem, `/etc/resolv.conf` is configured as a relative symbolic link:
   ```
   /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
   ```
5. **Lookup Path:** Any application calling standard C library resolver routines (`getaddrinfo(3)`, `gethostbyname(3)`) reads `/etc/resolv.conf`, queries `127.0.0.53:53`, and `systemd-resolved` forwards the query to upstream DNS servers.

### 2.2 The Chroot Pollution Mechanism

When entering the Ubuntu filesystem from WSL2, DNS resolution is required inside the chroot session. A common naive implementation pattern is copying the host's `/etc/resolv.conf` into the chroot target:

```sh
# ANTI-PATTERN (Destructive Copy):
cp -L /etc/resolv.conf /mnt/host/wsl/PHYSICALDRIVE1p4/etc/resolv.conf
```

The `-L` (`--dereference`) flag instructs `cp` to follow the symlink. Instead of updating the link target, `cp` removes the symbolic link at `/etc/resolv.conf` and creates a **regular static file** containing WSL2's internal configuration:

```ini
# /etc/resolv.conf (Overwritten on physical disk)
# This file was automatically generated by WSL.
nameserver 172.28.128.1
```

### 2.3 The Bare-Metal Failure Mode

When the computer is subsequently rebooted into bare-metal Ubuntu:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        BARE-METAL UBUNTU RUNTIME                       │
│                                                                        │
│  Wi-Fi Interface (wlan0): 192.168.1.105/24 (DHCP)                      │
│  Default Gateway:         192.168.1.1                                  │
│  Upstream DNS (from AP):  192.168.1.1 (stored in systemd-resolved)     │
│                                                                        │
│  [User Application]                                                    │
│         │                                                              │
│         ▼                                                              │
│  getaddrinfo("google.com")                                             │
│         │                                                              │
│         ▼ reads /etc/resolv.conf (STATIC FILE on SSD)                  │
│  Target Nameserver: 172.28.128.1:53                                    │
│         │                                                              │
│         ▼ routes via default gateway                                   │
│  UDP Packet: 192.168.1.105:53214 → 172.28.128.1:53                     │
│         │                                                              │
│         ▼                                                              │
│  Local Router (192.168.1.1) drops packet (RFC 1918 unroutable target) │
│         │                                                              │
│         ▼                                                              │
│  [TIMEOUT after 5000ms] → "Temporary failure in name resolution"      │
└────────────────────────────────────────────────────────────────────────┘
```

The IP `172.28.128.1` is the virtual gateway of the Windows Hyper-V vEthernet adapter. In a bare-metal boot, this interface does not exist. Every DNS query is routed to a non-existent destination and discarded, causing an apparent total network outage despite a healthy physical Wi-Fi link.

## 3. Engineering Solution: The Non-Destructive Bind-Mount Paradigm

### 3.1 The Pattern Comparison

| Approach | Implementation | Disk State | Bare-Metal Safe? |
|:---|:---|:---|:---:|
| **Static Copy (Anti-Pattern)** | `cp -L /etc/resolv.conf $ROOT/etc/resolv.conf` | Overwrites symlink with static file | ❌ Destructive |
| **Static Symlink to /run** | Symlink to non-existent `/run` in chroot | Unchanged, but DNS fails in chroot | ❌ Broken in chroot |
| **Transient Bind-Mount (Engineered)** | `mount --bind /etc/resolv.conf $ROOT/etc/resolv.conf` | Symlink preserved on disk; masked in-memory | ✅ Safe everywhere |

### 3.2 Implementation Details

In `scripts/enter_ubuntu.sh` and `scripts/start_sshd.sh`:

```sh
ROOT="/mnt/host/wsl/PHYSICALDRIVE1p4"

# Non-destructive bind-mount:
# Overlays WSL2's active resolv.conf onto the mount point in VFS memory.
# Does NOT modify the underlying ext4 inode or remove the symbolic link.
if [ -f /etc/resolv.conf ]; then
    mountpoint -q "$ROOT/etc/resolv.conf" || mount --bind /etc/resolv.conf "$ROOT/etc/resolv.conf" 2>/dev/null
fi
```

### 3.3 Clean Teardown

In `scripts/eject_ssd.ps1`:

```powershell
# Unmount the transient bind-mount before unmounting the root filesystem
wsl sh -c "sync; umount /mnt/host/wsl/PHYSICALDRIVE*p4/etc/resolv.conf 2>/dev/null; sync"
```

Once unmounted, the underlying symbolic link (`/etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf`) is immediately exposed and active for the next bare-metal boot.

## 4. Verification & Diagnostics Checklist

To diagnose DNS health on bare-metal Ubuntu:

```bash
# 1. Verify /etc/resolv.conf is a symlink, NOT a regular file
ls -la /etc/resolv.conf
# Expected output:
# lrwxrwxrwx 1 root root 39 /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf

# 2. Check systemd-resolved status
systemctl status systemd-resolved

# 3. Inspect active DNS servers per interface
resolvectl status

# 4. Test DNS resolution via local stub resolver
resolvectl query google.com

# 5. Direct test against public DNS bypass
dig @8.8.8.8 google.com +short
```

If `/etc/resolv.conf` was accidentally converted to a static file, restore it with:

```bash
sudo rm -f /etc/resolv.conf
sudo ln -s ../run/systemd/resolve/stub-resolv.conf /etc/resolv.conf
sudo systemctl restart systemd-resolved
```
